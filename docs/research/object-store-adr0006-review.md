# ADR-0006 adversarial review

Verdict: **accept-with-amendments**. Produced by a five-lane verification sweep (ADR-20 spec,
pinned nats.js obj, nats-server v2.14.5 + revision fidelity, Effect rc.111 Schema claims) and an
adversarial adjudication against ADRs 0001-0005, STYLE.md, and the shipped seam code. This digest
is the actionable record for amending [adr-0006](../architecture/adr-0006-object-store-stream-and-schema-boundary.md)
and [object-store-slice-scoping.md](../architecture/object-store-slice-scoping.md) before acceptance.

## Adjudication summary

The decision set survives adversarial verification and should not be redrafted: the three load-bearing choices — implementing over the private JetStream substrate rather than `@nats-io/obj` (decisions 1-2), metadata-PubAck-as-commit with a non-purging ambiguity path (decisions 3-4), and whole-value-only Schema integration (decisions 5-6) — were each confirmed against primary sources, and two turned out to be understated rather than overstated. The pinned client's failure path does not merely orphan storage; it can leave live metadata pointing at a purged chunk subject, after which every read hangs forever because the pump terminates only on a per-message pending signal that never arrives. And `@nats-io/obj` has no lossless revision path at all, which converts decision 1 from a backpressure argument into a correctness argument. What blocks acceptance is text, not design, in four groups. First, sourcing: every external line range I checked is wrong — nats.go `message.go` is 535 lines and is cited at 1541-1575 (the sole citation for decision 8's CAS mechanism), ADR-20 is 463 lines and is cited at 430-582, two refs point at unpinned `main`, and two independent lanes refuted six of seven nats.js ranges. Since these documents are the evidence base for the whole slice, undereferenceable citations are a credibility blocker, not a typo. Second, decision 9 would introduce a safe-integer `ObjectRevision` narrower than the `bigint` already shipped in `Kv.ts` and the substrate seam, contradicting ADR-0004's own stated scope; the ruling is to keep the branded `bigint`, move the gate to the ADR-0002 wrap adapter, require `lastMessageForSubject` over DIRECT.GET with `Schema.BigIntFromString`, and amend ADR-0004 with the exact contract in Amendment 1 — at zero code cost, since no `BigInt(` exists in the repo yet. Third, decisions 2, 3, 4 and 7 require substrate operations the shipped seam does not have (byte-window buffer with refill threshold, `purge`, and nine `StreamConfig` fields); notably the byte window is not new scope but a gap ADR-0005 already ruled and the seam never closed, so ADR-0006 should authorize the extension explicitly. Fourth, four ADR-20 rules are stated wrong or missing — delete-of-absent is an error not a success, link creation cannot be create-only because three of four spec naming rules require overwrite, UpdateMeta is limited to name/description/headers, and Put on a link is forbidden — plus the mtime delta is attributed to behavior ADR-20 actually prescribes. Eighteen amendments; nine of the ten open decisions are ready to rule now, with only the reconnect-resume parameter, the permission grammar, and the load-derived defaults genuinely needing live probes. One bookkeeping note for the adjudicating owner: the scoping doc carries nine open decisions (items 2-10) plus blocker 1, not eight; all nine are ruled above.

## Contradictions ruled

### ObjectRevision as a branded safe-integer contradicts ADR-0004's scope and the shipped bigint surface

REJECT the safe-integer domain type. ADR-0006 decision 9 and scoping blocker 1 propose `ObjectRevision` be a branded safe-integer with typed failure. The shipped substrate already commits to bigint: `publish(...): Effect<bigint, ...>` and `PublishOptions.expectedLastSubjectSequence?: bigint`; shipped KV already ships `KvEntry.revision: bigint` and `update(key, value, expected: bigint)` with no gate. A safe-integer ObjectRevision would create two incompatible revision types for the same JetStream sequence flowing into one substrate publish, and would reject values the pure in-memory interpreter can legitimately produce (it has no `number` anywhere). Resolution: `ObjectRevision` is a branded bigint identical in kind to the KV revision; the safe-integer gate moves to the ADR-0002 wrap adapter, the only place a JSON `number` exists. Primary fix is upstream of the gate: implement `lastMessageForSubject` over `$JS.API.DIRECT.GET` and decode the `Nats-Sequence` header string with `Schema.BigIntFromString`, which is lossless end-to-end and needs no gate at all.

Evidence: ADR-0004 L8 "Stream sequences and KV revisions are `bigint` throughout the substrate and domain layers"; C:\Users\kokok\Dev\effect-nats\src\internal\JetStreamSubstrate.ts:38 `readonly expectedLastSubjectSequence?: bigint` and :113-121 `publish(...): Effect.Effect<bigint, ...>`; C:\Users\kokok\Dev\effect-nats\src\internal\Kv.ts:35 `readonly revision: bigint`, :117-121 `update(key, value, expected: bigint)`; ADR-0006 L61-64 and scoping L436-442. Lossless path: nats-server v2.14.5 server/stream.go:5899 direct-get single reply header set `Nats-Stream/Nats-Subject/Nats-Sequence/Nats-Time-Stamp`; effect 4.0.0-rc.111 node_modules/effect/dist/Schema.d.ts:8525-8556 `BigIntFromString` with `^-?\d+$` guard. Irrecoverable path: nats.js@3a7b736 obj/src/objectstore.ts:568 `info.revision = ack.seq;` and :420-421 `const soi = m.json<ServerObjectInfo>(); soi.revision = m.seq;`, both JSON numbers via jetstream/src/jsbaseclient_api.ts:45-47 plain `JSON.parse`.

### Outcome ledger models delete-of-absent as a success value, contradicting ADR-20 and its own capability signature

CORRECT the ledger and add the delta. Verified first-hand at the pinned ADR-20 (463 lines, md5 d59875aefe5777debd67688d96156127): line 385 "* It's acceptable to no-op for an object that is already deleted." and line 386 "* It's an error to delete an object that does not exist." ### "Link creation is create-only at the destination metadata subject" directly violates three of ADR-20's four link naming rules

## Amendments required before acceptance

### Amendment 1 — ADR-0006 decision 9 + Consequences bullet 5, and ADR-0004 Decision (whole section) — RULING ON SCOPING BLOCKER 1

Amendment 1 (blocking). Replace ADR-0006 decision 9 with: "9. Guarded mutation requires an exact revision. `ObjectRevision` is a branded `bigint`, identical in kind to the KV revision already shipped in `src/internal/Kv.ts`, and is always the sequence of the object's current metadata message. It is obtained losslessly from the direct-get `Nats-Sequence` header, never from a JSON response body. Where the wrap adapter can obtain a sequence only as a JSON number, it fails with a typed `SequenceNotProvablyExact` rather than converting; that gate lives at the ADR-0002 seam, not in this slice's domain types. ADR-0004 is amended accordingly and must be re-accepted before this ADR is accepted." Replace the Consequences safe-integer bullet with: "Failing closed on a non-exact sequence is necessary, not conservative: two distinct uint64 sequences above 2^53 decode to the same JavaScript number, so a stale rounded revision can equal a different newer exact server revision and make the expected-sequence header pass. The same rule covers `size`, which is `uint64` on the wire (ADR-20:198); `chunks` is `uint32` (ADR-20:201) and is safe." Replace ADR-0004's Decision section in full with: "Stream sequences and KV/Object Store revisions are `bigint` throughout the substrate and domain layers. JetStream sequences are unsigned 64-bit on the wire, which exceeds `Number.MAX_SAFE_INTEGER`, so `number` silently corrupts above 2^53. A `bigint` is honest only where it was parsed from the wire's decimal string. Official nats.js surfaces `number` for sequences, and `JSON.parse` has already rounded the value before any conversion runs: `BigInt(n)` is exact for every double and therefore launders an already-wrong value into an authoritative-looking integer. `BigInt(n)` is not a fidelity remedy and must not appear at any wire boundary. The wrap adapter (ADR-0002) is the single boundary and obeys three rules. (1) String-borne sequences are lossless: sequences read from a header — `Nats-Sequence` and `Nats-Last-Sequence` on a direct get, the ack-subject tokens of a `JsMsg` — are decoded with `Schema.BigIntFromString`, whose `^-?\\d+$` guard makes a malformed header a typed decode failure. `lastMessageForSubject` MUST be implemented over `$JS.API.DIRECT.GET` for this reason; the JSON `STREAM.MSG.GET` path is not an acceptable revision source. (2) JSON-number sequences are lossy and fail closed: a sequence that reaches the adapter only as a JSON number (`PubAck.seq`, `StreamState.first_seq`/`last_seq`, `SequenceInfo`) is converted only when `Number.isSafeInteger` holds; otherwise the operation fails with a typed `SequenceNotProvablyExact` carrying the operation and the raw response. No unchecked `BigInt(n)` ships. (3) Client-to-wire is lossless only when the adapter formats the `bigint` itself: the expected-last-subject-sequence header is written as `${bigint}`; interpolating a `number` is forbidden. The public `Revision`/`ObjectRevision` types are branded `bigint`. The safe-integer gate is an adapter-boundary property, never a narrowing of a domain type." Also replace ADR-0004's second consequence bullet with: "The wrap adapter owns the single number-to-bigint decision point and its test; the substrate and domain layers never see a `number` sequence." Correct the scoping blocker-1 sentence to attribute the loss to `JSON.parse`, not to the conversion.

Why: The current ADR-0004 clause "wire-to-client values pass through `BigInt(n)` unchanged" is literally true and materially misleading — `BigInt(n)` is exact for every double, so the error is 100% upstream in `JSON.parse` and the conversion merely laundered it. The current ADR-0006 decision 9 fixes that by narrowing the domain type, which contradicts ADR-0004's own scope and the shipped bigint surfaces in `Kv.ts` and the substrate seam, and would make Object Store and KV structurally different for the same JetStream sequence. Evidence: nats.js@3a7b736 obj/src/objectstore.ts:172-178 vs obj/src/sha256.ts:43 `let backend: Sha256Backend = "js";`, and `Objm.open` at :128-166 with no gate; nats-server v2.14.5 server/filestore.go:4960-4987 (unconditional MaxBytes branch with `asl=false`) and :4966-4969 / server/memstore.go:210-237 (rollup exemption gated on `DiscardNewPer`); nats.js objectstore.ts:999-1006 never sets `max_msgs_per_subject`; server/store.go:51, server/stream.go:7049,7064-7067, server/jetstream_errors_generated.go:885 (503/10077).

### Amendment 18 — scoping "First-class Effect Schema integration" typed-values sketch (L260-274)

Pin two type details before the compile spike: (a) the `SchemaWithUint8ArrayEncoded` bound must use `Uint8Array<ArrayBuffer>`, not the bare `Uint8Array` (`ArrayBufferLike`) that `Schema.Uint8Array` declares — they do not unify with the pinned bytes codecs without the same cast Effect itself uses; since decision 1's body type is `Stream<Uint8Array, ...>`, the read path should allocate its own concatenation buffer, which infers `Uint8Array<ArrayBuffer>` cleanly. The Schema surface is otherwise fully validated: every named or implied API type-checks under the repo's own tsconfig at TS 7.0.2, so the doc's caveat "illustrative until a compile spike" can be discharged for this section once the placeholders are defined.

## Open-decision rulings

### #2 — Accept or reject the private JetStream implementation of Object Store read/watch required for bounded producer-side behavior. [ready-to-rule]

ACCEPT, and note it is already forced by two accepted ADRs rather than being an open choice. Producer-side evidence: the pinned client's `get` pumps a push consumer into a ReadableStream built with no queuing strategy and no `pull()`, never consulting `desiredSize` (zero occurrences of desiredSize/highWaterMark/QueuingStrategy in the whole module and its tests); `watch` pushes into `QueuedIteratorImpl`, whose `push` is a plain array append with no capacity, no drop policy and a `void` return, so the synchronous JsMsg callback cannot suspend; and `list()` is literally a runCollect over that same unbounded watch iterator — a named upstream counterexample to the doc's own rule that no public Stream is implemented by runCollect. ADR-0002's guardrail already requires bridging via bounded queues and forbids upstream async iterators, and ADR-0005 requires a pull window with a refill threshold that `@nats-io/obj` cannot express. The decisive additional argument is correctness, not backpressure: `@nats-io/obj` has no lossless revision path at all — both `info.revision = ack.seq` and `soi.revision = m.seq` are JSON numbers — so an Object Store slice built on it cannot honor ADR-0004's contract under any wording. Acceptance carries the substrate extensions in Amendment 3.

### #3 — Is cleanup-pending returned in every committed mutation result, emitted only as diagnostics plus a maintenance journal, or both? [ready-to-rule]

BOTH. Return `cleanup: Complete | Pending` on every committed mutation result AND emit a diagnostic record for an operator-visible reconciliation queue. ADR-0005's rule that "every acceptance boundary keeps its own name and result" supports the in-result form; the diagnostic form is required because the leak is unbounded and invisible otherwise. Concretely: the pinned client captures `old` once before any bytes are uploaded and purges `old.nuid` after commit, so a writer that loses a concurrent replacement race purges a stale snapshot and orphans one full object permanently — no client operation ever reclaims it. The purge failure is additionally swallowed by design. Ship with the Amendment 10 correction (purge the NUID the commit actually superseded, re-read at commit time), otherwise the in-result `Pending` will under-report.

### #4 — Decide the zero-byte Stream element convention via an official-client conformance test. [ready-to-rule]

RULE: emit ZERO elements, and strike the stated method — there is no upstream authority to defer to. The two official clients already disagree: nats.js returns a stream that enqueues one empty `Uint8Array` then closes, while nats.go returns a result whose reader is nil so it yields zero reads. ADR-20 says nothing about zero-byte objects. The only upstream test touching zero-byte reads concatenates the stream and asserts total length 0, so it does not pin framing either way; the one test that DOES observe framing covers non-empty objects only. Zero elements is the Effect-idiomatic empty Stream, matches nats.go, and keeps size and digest identical; record it as an explicit divergence from nats.js element framing. Non-empty framing IS pinned upstream (one element per stored chunk, in the writer's chunk size, in order) and must be matched. Note the neighbouring unstated branch (Amendment 14 item 12): both clients skip digest verification for empty objects entirely, so "digest, size and chunk count verified" needs an explicit empty-object rule.

### #5 — Decide canonical modified time and universal metadata-rollup behavior for the two ADR-20-versus-NATS.js deltas. [ready-to-rule]

RULE BOTH. (a) modifiedAt: the metadata message's SERVER timestamp, per ADR-20:77-78 and :211, taken from the direct-get `Nats-Time-Stamp` RFC3339Nano header (or `JsMsg.timestampNanos`, which is BigInt-parsed from a decimal string) — explicitly NOT `JsMsg.info.timestampNanos`, which is `parseInt`-derived and already quantized to 256 ns at present-day epoch nanoseconds. This is the same lossless-string rule as the revision blocker and should be settled by it. Additionally return a client-generated UTC time from `put` as ADR-20:77 prescribes, but never write it into the stored payload, and expose the two as distinct fields. (b) rollup: enforce `Nats-Rollup: sub` on EVERY Effect metadata mutation including link and update, per ADR-20:54 ("always rolled up"), and record the pinned client's omission on link/update as a documented delta. Source the header constant from ADR-8 and the server, not ADR-20 (which never names it) — the repo already has `rollupHeader`/`rollupSubject` in the substrate. Two consequences to write down: `RollupNotPermitted` becomes a typed failure (Amendment 10b), and rollup on update destroys that name's metadata history, which the rename deferral should cite.

### #6 — Decide reconnect policy for an in-progress pull read; resume must prove chunk position and ordering. [needs-live-probe]

RULE the policy now; probe the parameter. Policy: per ADR-0001 decision 1 the read never owns reconnection — it observes supervisor status, and no Effect retry layer stacks on top (that ADR names Object Store explicitly). Resume IS provable here in a way KV watch is not, because an object is immutable by NUID: chunks live on the single subject `$O.<bucket>.C.<nuid>` with contiguous stream sequences, a known total count, a known total size and a whole-object digest, all three verified terminally. So resume is permitted when the adapter can name the next expected chunk sequence AND re-confirm the object's metadata revision is unchanged; otherwise the stream fails typed and the caller restarts from metadata. A mis-resume cannot pass silently because count, size and digest all gate the terminal success. Probe needed for the parameter: against each declared real-server version, prove a reconnect gap cannot silently skip or duplicate a chunk under a pull consumer, and measure whether the consumer survives leader loss — this is the same untested reconnect-gap branch the outcome ledger already names for the body Stream.

Probe: Against each declared nats-server version: create an OBJ bucket, start a bounded pull read of a multi-chunk object, force a reconnect (kill the connection, then leader loss in a clustered setup) mid-read, and assert that either every chunk sequence is delivered exactly once in order or the stream fails typed. Repeat with the consumer deleted server-side.

### #7 — Decide the first supported Schema byte formats (recommended: direct bytes and UTF-8 JSON, both with mandatory finite encoded-size bounds). [ready-to-rule]

ACCEPT the recommended set, with one correction and one exclusion. Correction: UTF-8 JSON with a `Uint8Array` encoded side is NOT a composition of shipped pieces — the pinned Effect ships no UTF-8 bytes↔string schema or transformation, and `Schema.fromJsonString` is String-encoded; the only bytes↔string codecs are base64/base64url/hex. The glue is a few lines of `TextEncoder`/`TextDecoder` in a `decodeTo` and has been compile-verified, but the plan must say so rather than implying it is free. Exclusion: do NOT adopt `Msgpack.schema`, despite it shipping ready-made with exactly the required `Uint8Array` encoded side — it lives under `effect/unstable/*`, and taking a dependency on unstable surface is a policy question STYLE.md's upgrade discipline does not currently cover; if it is ever adopted, the ADR needs a stated position on `unstable`. Keep mandatory finite bounds, kept outside the schema per Amendment 12.

### #8 — Decide whether an explicitly named unconditional parity capability is ever needed. [ready-to-rule]

RULE: not in the first slice, and not as an omitted condition — but the ADR must resolve the one case where its absence conflicts with the spec. The default is well justified: the pinned client's guard is optional and absent by default, so `@nats-io/obj` parity means last-writer-wins, and ADR-0003 sets the precedent that this repo deliberately breaks parity where the loose form fails silently. The unresolved case is links: ADR-20 REQUIRES that naming a link over an existing link, a bucket link, or a deleted name succeed, which a strict `CreateOnly | Replace(rev)` surface cannot express without a read the doc itself forbids as a client-side pre-check. Resolve that by giving link creation an explicit expected-revision condition over the destination subject with the four spec outcomes enumerated (Amendment 6), not by introducing an unconditional write. A named `putUnconditional` remains possible but requires its own ADR and may never be a default or an omitted condition.

### #9 — Decide the deployment/permission profile for applications needing CAS enforced against non-Effect clients with direct Object Store write access. [needs-live-probe]

The shape is settled — route mutations through a controlled writer service/account and deny direct publish on the bucket's subject space to every other credential; the ADR's Consequences already states the honest limit (client-side CAS is opt-in per publish, not a bucket lock). But the concrete subject grammar must be probed before it is published as a recipe, because nats-server's own JetStream deny lists use `$OBJ.>`, which does NOT match the real Object Store subject space `$O.<bucket>.>` — so the obvious deny pattern is wrong and a copy-paste recipe would silently fail open. Until the probe lands, ship the deployment WARNING (already in the doc) without a recipe.

Probe: On nats-server v2.14.5, define an account with two users: a writer permitted to publish `$JS.API.>` and `$O.<bucket>.>`, and a reader permitted `$JS.API.>` but denied `$O.>`. Assert (a) create/replace through the writer succeeds, (b) a direct metadata publish by the reader is denied, (c) direct-get reads by the reader still succeed, and (d) the reader cannot bypass the deny via `$JS.API.STREAM.MSG.*` or a rollup publish. Record the exact working allow/deny grammar.

### #10 — Set profile defaults only after real-server load measurements (requested/effective chunk size, PubAck RTT, replacement peak, read memory, consumer usage). [needs-live-probe]

KEEP as an explicit non-decision, but bind it to a gate so it cannot drift into invented defaults: no numeric default ships until its measurement exists; until then every knob is the tagged `Default` variant per ADR-0005's no-sentinel rule, and `Default` for chunk size resolves to ADR-20's 128 KiB (verified at ADR-20:86) clamped by the `effectiveChunkBytes` formula. One provenance correction is needed regardless of measurement: the `min(requested, max_payload)` clamp is a NATS.js-only behavior — nats.go performs no such clamp and ADR-20 says only "Clients may tune this as appropriate" — and the clamped value is written back into the object's own `options.max_chunk_size` metadata, so a clamped write is observable on the wire and a Go reader sees a chunk size a Go writer would never produce. Label it a parity decision, not conformance. Also note the three enforcement points are distinct: connection `max_payload` (protocol level, and a violation CLOSES the connection rather than failing a PubAck), stream `max_msg_size`, and the encoded-subject budget bounded by `MAX_CONTROL_LINE_SIZE` — the last is a different limit with a different failure mode and must not be collapsed into the metadata-bytes setting.

Probe: The gate-9/10 load harness against each declared server version, reporting requested vs effective chunk size, PubAck round-trip time, replacement peak bytes, per-read memory high-water mark, and concurrent consumer count; plus a direct probe of the max_payload violation path to confirm it closes the connection rather than returning a typed PubAck error.
